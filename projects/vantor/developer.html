Engineering notes · Vantor

Under the hood.

A technical reading of Vantor: its architecture, component boundaries, interfaces, runtime behavior, security assumptions and implementation constraints.

01. System architecture

The repository documents a Windows-only C++20 system split into a service, backend, common IPC/crypto code and Qt user interface. The design prioritizes component boundaries and uses Windows-native facilities for service lifecycle, process integrity and protected storage.

Qt desktop client ⇄ authenticated local gRPC backend ⇄ Windows service / scanner → signature store and quarantine; anti-tamper monitors process and binary integrity

02. Component responsibilities

  • service/: Win32 Service Control Manager entry points, scanning, configuration, named-pipe IPC, anti-tamper and real-time filesystem monitoring.
  • backend/: gRPC endpoints, signature storage and archive inspection.
  • common/: reusable crypto, named-pipe and logging utilities.
  • proto/: Protocol Buffers contract for service/backend operations.
  • Qt client: desktop dashboard, scanning interactions and quarantine/policy presentation.

03. Interfaces and protocols

  • gRPC with Protocol Buffers connects the desktop/backend surfaces.
  • Windows named pipes provide a restricted local IPC path to privileged service functionality.
  • SQLite stores signature metadata; a memory-mapped Bloom index accelerates negative lookups.
  • CMake and vcpkg define the native build and dependency environment.

04. Runtime and data flow

The Qt client sends operations through the backend boundary. The service owns privileged scanning and filesystem-monitoring responsibilities. This separation is intended to limit what the interactive application can do directly.

05. Security considerations

The documented controls include WinVerifyTrust checks, runtime text-section hashing, API hook and debugger detection, CFG/ASLR/DEP build mitigations, DPAPI-protected configuration and an AES-256-GCM quarantine vault with a DPAPI machine-protected key. These are mechanisms in the design, not proof of complete protection against a capable attacker.

06. Build and validation

C++20, CMake, vcpkg and Qt 6 form the documented native toolchain. The repository also documents WiX-based MSI packaging and backend tests. Exact build status should be read from the current CI run and release artifacts.

For an interview or technical review, use the repository's current build files, automated checks, release notes and source as the authoritative evidence for what is implemented at a particular commit.

07. Known limits and claims discipline

No kernel driver is claimed. Anti-tamper is described as user-mode. Do not market the project as production-ready antivirus or imply threat-detection effectiveness without independent tests.

These notes are intended to support a serious technical discussion. They distinguish documented design intent from independently verified production guarantees.

Documentation is versioned with the portfolio. Repository source and release notes take precedence when implementation details change.
