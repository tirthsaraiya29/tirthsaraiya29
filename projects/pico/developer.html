01. System architecture

Pico is a Rust workspace with dedicated crates for core types, security, platform adapters, inference, decision ranking, learning, tools, audio, voice, memory and orchestration, plus CLI and desktop applications.

Microphone → audio pipeline / VAD → ASR and normalization → tool retrieval + candidate ranking → clarification / confirmation policy → platform tool execution → objective verification

02. Component responsibilities

  • pico-audio: capture buffers, resampling and audio-format handling.
  • pico-voice: speech recognition, normalization, VAD and speech synthesis adapters.
  • pico-decision / pico-inference: intent retrieval, candidate ranking and confidence logic.
  • pico-orchestrator: clarification, confirmation, tool dispatch and result coordination.
  • pico-security: execution boundaries and request validation.
  • pico-platform / pico-tools: operating-system-specific capabilities.
  • pico-memory: local persistence and audit-oriented state.
  • pico-cli and pico-desktop: headless runtime and companion interface.

03. Interfaces and protocols

  • Workspace crates communicate through Rust types and internal async boundaries.
  • Tokio provides asynchronous runtime services; Serde/TOML support configuration and data contracts.
  • SQLite is used for persisted state and local memory.
  • Audio input uses platform backends such as WASAPI or ALSA, with resampling to the model-facing rate.

04. Runtime and data flow

The desktop companion is separated from the assistant runtime. The pipeline distinguishes capture, recognition, decision, clarification, confirmation, tool execution and objective verification so failure at one stage need not be disguised as success.

05. Security considerations

The README documents fail-closed path sandboxing, UNC/ADS/device-name and symlink-chain checks, SSRF address filtering and DNS pinning, single-use context-bound confirmations, escaped SQL LIKE queries and redacted audit logging.

06. Build and validation

The root Cargo workspace lists the application and internal crates. Release builds use optimized code generation, LTO and stripped binaries. Validate the current CI matrix before quoting supported OS versions or benchmark numbers.

For an interview or technical review, use the repository's current build files, automated checks, release notes and source as the authoritative evidence for what is implemented at a particular commit.

07. Known limits and claims discipline

Do not quote benchmark accuracy without the precise test suite and current run. Speech output and action execution are active reliability work; the portfolio should not imply every requested operating-system action always succeeds.

These notes are intended to support a serious technical discussion. They distinguish documented design intent from independently verified production guarantees.

Documentation is versioned with the portfolio. Repository source and release notes take precedence when implementation details change.
