A personal engineering journal

Notes from the workbench.

Not every idea needs a 2,000-word article. This is where I keep the short observations, design instincts and lessons that shape how I build.

Systems thinking

Security starts at the boundary

The interesting part of a system is often not the component itself; it is the seam between two components. A service and a desktop session. A phone and a workstation. A browser and a local model endpoint. The engineering question is what may cross that seam, what proves it is allowed, and what happens when the proof is missing. I keep coming back to that pattern because it turns vague security language into concrete interfaces, permissions and failure paths.

Local-first AI

Inference is a hardware problem, too

A model that technically loads is not necessarily a model that feels usable. Weight size is only the beginning: KV cache, context length, runtime overhead, activation memory, bandwidth and thermal behavior all matter. A good model-selection experience should help people understand those trade-offs before they spend an evening downloading something their machine cannot run comfortably.

Product engineering

Readable is a feature

A powerful application that makes people work to understand it still has a product problem. Readability is not decoration added after the engineering is finished. It affects how quickly someone can find a setting, recover from a mistake, understand a result and trust the software. The same principle applies to code, documentation and user interfaces: clarity reduces the amount of invisible work a person has to do.

Reliability

Don't report success before verifying it

An assistant that says “done” because it emitted a command has confused intention with outcome. The same thing happens in ordinary software when a button click is treated as proof that a transaction completed. I prefer explicit states: requested, accepted, running, verified, failed. It is less theatrical, but much more useful when something matters.

Learning in public

Unfinished work is still worth documenting

An archived experiment can be a useful engineering record. It shows which direction was explored, what architecture seemed promising and where implementation stopped. The trick is to label it honestly. A sketch should not look like a released product, and a prototype should not borrow the confidence of a mature system.
